# 茅台 2024 年报 RAG 问答系统

把一份 143 页的中文年度报告，变成一个能听懂口语、答案带页码、查不到就明说的问答系统。

Streamlit 界面 + 父子块索引 + BM25/向量混合召回 + 交叉编码器精排 + 多轮指代消解。

---

## 为什么做这个

财务报告问答不是普通文档问答。同一份年报里同时存在四个坑，通用 RAG 在这四条上都会翻车：

| 问题 | 具体表现 | 通用 RAG 的失败方式 |
|---|---|---|
| **口径多重** | 归母净利润 / 净利润、合并报表 / 母公司报表、营业收入 / 营业总收入 | 把不同口径的数字混着引用，答案看着对、其实错 |
| **数字不能被加工** | 营业收入 170,899,152,276.34 元 | 模型自行换算成"1709 亿"或做加减推算，原文找不到依据 |
| **页眉污染** | 每页顶部都有相同的公司名与页码两行 | 每个切片都带上这段无信息文本，拉低所有检索的相关度 |
| **大量问题本就不该有答案** | 研发人员数量、某国销售额、董事长手机号 | 用行业常识编一个，且编得很像真的 |

这个项目的每个设计决策，基本都对应上表里的某一行。

---

## 技术链路

```
PDF 解析 → 页眉正则清洗 → 父子块切分（父 1500 / 子 300 重叠 50）
        → 通义千问 text-embedding-v4 向量化 → Chroma 索引
        → 查询改写（口语→年报术语）
        → BM25(jieba) + 向量 混合召回（RRF）
        → bge-reranker-base 交叉编码器精排
        → 父块回填组装上下文
        → DeepSeek 生成（强制页码引用、强制拒答）
        → RAGAS 四指标评测 + 拒答准确率单独统计
```

**技术栈**：Python 3.13 / LangChain / Chroma / rank-bm25 + jieba / sentence-transformers / 通义千问 text-embedding-v4 / DeepSeek / LangGraph / RAGAS / Streamlit

## 五个关键设计决策

### 1. 父子块索引，而不是直接切 300 字

小块检索准（语义集中），大块给模型的上下文全（不丢上下文）。所以切成两层：**子块 300 字参与检索，命中后回填它所属的 1500 字父块**送给模型。

父块**零重叠**——它不参与检索，重叠只会让同一段文字在上下文里重复占用 token。子块保留 50 字重叠，防止一句关键结论被切在两块中间。

回填时按 `parent_id` 去重：同一父块下命中多条子块，只取精排分数最高的一条，否则一个父块会把上下文挤满。

### 2. 先清洗页眉，再切分

清洗顺序很容易写错。如果在切分之后清洗，页眉已经混进每个 chunk，只能事后补救；正确做法是**在切分之前对整页文本做正则清除**：

```python
hdr = re.compile(
    r"^\s*贵州茅台酒股份有限公司\s*\d*\s*年年度报告\s*$\s*\n?\s*\d+\s*/\s*\d+\s*$\s*",
    re.MULTILINE,
)
```

不做这一步的后果很隐蔽：检索会稳定命中"贵州茅台酒股份有限公司 2024 年年度报告 12/143"这种文本，因为它跟任何问题的字面相似度都不低，但信息量为零。

### 3. 混合召回：向量负责语义，BM25 负责数字

财报里最有价值的信息是精确数字和专有名词，而这恰好是稠密向量的弱项——`170,899,152,276.34` 和 `147,693,604,994.14` 在向量空间里几乎是同一个点。BM25 能精确匹配到数字串本身，向量负责处理"赚了多少钱"和"归母净利润"之间的语义距离。

两者用 RRF（倒数排名融合）合并，权重作用在**排名**上而非分数上，避免两种检索的分数量纲不一致。

中文分词用 `jieba.cut_for_search`——搜索模式会把长词再切一遍，保证"茅台"这类短词一定能被切出来。**建索引与查询必须用同一个 `preprocess_func`**，否则 BM25 会静默返回全 0 分且不报错。

### 4. 查询改写：把口语对齐到年报术语

用户问"茅台去年赚了多少钱"，年报里写的是"归属于上市公司股东的净利润"。中间隔着一层术语鸿沟，靠嵌入模型硬扛效果不稳定。

改写节点做三件事：补全实体（茅台→贵州茅台）、术语对齐（赚了多少钱→归母净利润）、保留疑问焦点。同时把相对时间（"去年"）按报告年度写死，不按系统当前日期推算。

**实测 Context Recall 从 0.87 提升到 0.97。**

代价是改写可能引入同指标不同口径的片段，所以生成侧必须配合口径约束（见下一条）。

### 5. 拒答是一等公民，不是兜底

提示词里把"资料中没有的一律回答『资料中未提及』"写成硬约束，并明确禁止用行业常识、往年数据、逻辑推理来填补。同时约定：同一指标出现多个版本时逐一区分并注明口径，未指明口径时默认合并报表本期数据。

但**拒答做得好，RAGAS 分数反而会掉**——正确拒答的陈述在原文里找不到依据，Faithfulness 低；"资料中未提及"这种短答案也无法反推出有效问题，Answer Relevancy 低。

所以评测集里把 5 条负样本单独拆出来，用关键词匹配单独算**拒答准确率**，不和可答类混在一起看平均分。

## 多轮对话里的指代消解

只挂 checkpointer 是不够的。用户追问"那它的增长率呢"，检索器拿到的是这七个字本身，召回必然跑偏。

真正的解法是在检索前加一个**指代消解节点**：先用对话历史把追问改写成独立问句（"它的增长率"→"贵州茅台2024年归母净利润的增长率"），再拿去检索。checkpointer 只负责历史存在哪，改写节点才负责让它起作用。

这个模式与评测互斥——多轮下同一个问题在不同对话位置会召回不同内容，所以 RAGAS 评测一律在单轮模式下跑，保证可复现。侧边栏留了开关。

## 评测

20 条测试集，四条明确的题型划分：

| 类型 | 条数 | 检验什么 |
|---|---|---|
| `fact` | 11 | 精确数值与事实能否答对 |
| `summary` | 2 | 需要跨段归纳的问题 |
| `colloquial` | 2 | 口语化提问，检验查询改写 |
| `negative` | 5 | 年报中不存在的信息，检验拒答 |

指标用 RAGAS 四项（Faithfulness / Answer Relevancy / Context Precision / Context Recall），判官为 `deepseek-chat`。

> 需要说明的偏差：判官与生成模型同源，存在 self-preference，分数偏乐观。要更严格，判官应换成不同家族的模型。

## 快速开始

```bash
# 1. 依赖（torch 建议装 CPU 版，体积小很多）
pip install torch==2.14.1 --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt

# 2. 配置密钥
cp .env.example .env   # 填入 DASHSCOPE_API_KEY 与 DEEPSEEK_API_KEY

# 3. 启动
streamlit run app.py
```

浏览器打开 `http://localhost:8501`。首次启动需要加载精排模型，约 60 秒；之后秒开。

仓库里已附带建好的 `chroma_db_v2/` 与 `store/`（两者必须来自同一次运行，不可混用），所以**不需要重建索引**。需要重建时跑 `test.ipynb` 的「3.2 建库」单元格，会调用约 72 次嵌入接口。

### 推荐的演示问题

| 问题 | 看点 |

## 踩过的坑

写下来是因为这些坑的共同点是**不报错、只出错**，排查成本远高于写代码本身。

1. **DashScope 兼容接口必须加 `check_embedding_ctx_length=False`**。LangChain 默认会先用 tiktoken 把文本编码成 token 数组，而 DashScope 只接受字符串，不加会报 `contents is neither str nor list of str`。
2. **BM25 的 `preprocess_func` 建索引与查询不一致时，不报错，直接全 0 分。** 结果是检索退化成纯向量，而且没有任何提示。
3. **RAGAS 的 `ResponseRelevancy` 只存在于旧路径 `ragas.metrics`**，`ragas.metrics.collections` 下的 `AnswerRelevancy` 是 v2 架构（需 `llm_factory` + `ascore`），不能传给 `evaluate()`。
4. **RAGAS 会导入 `langchain_community.chat_models.vertexai`**，当前 LangChain 版本已无此模块，需要塞一个空壳 ModuleType 才能导入成功。
5. **HuggingFace 直连不稳定**，`bge-reranker-base` 改走 ModelScope 的 `snapshot_download`。
6. **`chroma_db_v2` 与 `store` 必须来自同一次运行**。父块编号（`p0`、`p1`…）是当次生成的，混用会让上下文回填错位——答案开始引用不相关的页码，但不报错。

## 已知局限

- **单文档**。没有做跨年对比、跨公司对标，也没有接入多份年报的增量索引。
- **表格未做结构化解析**。PDF 里的表格按文本流切分，跨页表格可能断开，复杂表格的列对齐信息会丢失。要更准得上布局感知解析（如表格识别模型），这是下一步。
- **判官同源偏差**，评测分数偏乐观。
- **无检索缓存**，每次提问都实时走向量检索与精排，首次响应约 3–6 秒。
- 只覆盖 2024 年单一年度，时间归一逻辑写死在 `REPORT_YEAR`。
